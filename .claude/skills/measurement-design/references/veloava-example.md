# 実例: VeloAva（Strava連携のサイクリスト診断アプリ）

Next.js（Vercel）+ GA4。Stravaのライドデータからタイプを6キャラで診断し、Xでシェアさせて広げるアプリ。

## 計測の目的

- 「X投稿から来た人が診断に進んでいるか」「どこで離脱しているか」を判断する
- CV = ユーザーのシェアから人が来た（`share_inflow`）。当初は Xでポストのクリック（`share_x`）をCVにしていたが、投稿画面を開いただけで実際に投稿されたかは分からないため、シェアURLに `utm_campaign=user_share` を付けて着地を数える形に変えた

## イベント設計

| イベント | 発生箇所 | パラメータ |
|---|---|---|
| `diagnosis_start` | トップの期間ボタン | `period`, `predicted_type` |
| `share_x` | 結果ページの「Xでポスト」（投稿画面を開いた） | なし |
| `share_inflow` | ユーザーのシェアURLからキャラ紹介ページに着地（キーイベント） | なし |
| `share_card` | 保存・共有ボタン | `method` = share / download |
| `retry_diagnosis` | もう一度診断する | なし |
| `share_page_cta` | キャラ紹介ページの「あなたも診断する」 | なし |
| `ui_click` | その他のリンク | `button_id` |

ユーザー単位のカスタムディメンション `predicted_type`: 診断前にユーザー自身が選んだ「自分のタイプ予想」。Strava由来ではないので使える。

## 計測してはいけないもの

- 診断結果のキャラ・性別・統計（Strava API Policy 5.4: Strava由来の派生データを匿名・集計でも分析に使うことを禁止）
- 当初 `share_card` に `character_id` を付けていたが外した。「自分たちで生成した値だから大丈夫では」という疑問が出たが、Stravaのデータから計算した結果なので対象になる
- キャラ紹介ページ `/c/{character}_{sex}` をキャラ別に集計しない。集計ツール側でも `/c/` は合計だけ返す
- 「わからない形にして送る」案も出たが、加工しても同じデータとみなされ、監査で見つかれば意図的な違反扱いになるので不採用。代わりに「ユーザー自身の予想」を計測する設計にした（診断前のワクワク感にもなった）

## 見つかった不具合と経緯

1. **Xボタンが反応しない**: LINEのアプリ内ブラウザで `window.open` がブロックされていた → 通常のリンクに変更
2. **結果ページの人数が診断開始の2倍**:
   - 原因1: 動作確認用のプレビュー表示（`?preview=`）が計測されていた → config しないよう変更、集計側でも除外
   - 原因2: X/LINEのアプリ内ブラウザ → Stravaアプリ → Safari と切り替わり別人扱い → client_id を OAuth の state で持ち回り。リンカー（`_gl`）はブラウザが変わると無効になり、Strava経由で消えるので使えなかった
3. **Xでポスト43回が1人**: 開発者のテスト。ユーザー数で判断する
4. **予想タイプが `(not set)` だけ**: カスタムディメンション登録前のデータ
5. **判定結果がTTとスプリンターに7割偏る**: 計測ではなくロジックの問題。架空の5,000人でシミュレーションして発見、加重平均に直して各キャラ7〜26%に分散
6. **「週5.5回」が実感と合わない**: 件数で数えていた（Zwiftや1回の外出の分割で膨らむ）。実データと突き合わせ、乗った日数（週4.2日）に変更

## 数字の取り方

さくらのレンタルサーバー上のPHP製MCPサーバーに `ga_summary` / `ga_funnel` / `ga_trend` / `ga_predicted_types` を追加し、チャットから直接GA4の数字を取れるようにした。サービスアカウントのJWTをPHPだけで署名し、GA4 Data API の `batchRunReports` を呼ぶ（GA4 Data API は無料、上限超過はエラーで課金はない）。
