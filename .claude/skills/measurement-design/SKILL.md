# 計測設計

計測は「GAを入れる」ことではなく、**判断に使える数字を、正しく、取ってはいけないものを取らずに集める**こと。次の6段階で進める。依頼が途中の段階（例: 数字がおかしい）から始まっても、前の段階の前提（何をCVにしているか、何を計測してはいけないか）を先に確認する。

## 1. 目的とCVを決める

- その数字で**何を判断するのか**を1文で書く（例:「X投稿からの流入が診断につながっているか」）。判断に使わない数字は計測しない
- ファネルを書き出す。各段は「人が1つの行動をした」単位にする（例: トップ閲覧 → 診断開始 → 結果表示 → シェア）
- **CV（キーイベント）は専用のイベント名にする**。GA4のキーイベントはイベント名単位でしか指定できないため、`share` に `method=x` を付けるのではなく `share_x` のように分ける
- 命名: 英小文字のスネークケース、動詞か「対象_行動」で統一。補足はパラメータに入れる（`diagnosis_start` + `period`）
- パラメータは種類が少ない値にする（期間・方法・ボタンIDなど）。自由入力・ID・URL全体は入れない

## 2. 計測してはいけないものを先に洗い出す

実装より前にやる。後から外すのは大変で、規約違反は取り消せない。

- **外部APIの規約**: 外部サービスから取得したデータ（とそこから計算した値）を分析に使うことを禁じている規約がある。例: Strava API Policy 5.4 は、匿名化・集計した形でも分析・製品改善への利用を禁止。こうした値は、イベントのパラメータにも、ユーザープロパティにも、ページURL別の集計にも載せない。**値を加工・匿名化しても同じデータとみなされる**ので、偽装で回避しない
- **個人情報**: 氏名・メール・電話・外部サービスのユーザーIDなどをGAに送らない（GAの規約でも禁止）。URLのクエリに個人データが入る設計なら、ページURLごと送られる点に注意
- **代わりに使える値**: ユーザー自身の入力（アンケート・予想など）、アプリ側で決まる値（選んだ期間・初回/再訪・流入元）は使える
- 計測内容を増やしたらプライバシーポリシーも更新する

## 3. 実装する

- **ハンドラのあるボタン**は、クリック処理の中で直接イベントを送る
- **サーバー側で描画されるリンク**は、要素に `data-ga-event`（と `data-ga-id`）を付け、document へのクリック委任で拾う小さなクライアントコンポーネントを1つ置く。リンクごとに onClick を書かない
- **アプリ内ブラウザ対策**: シェアボタンを `window.open` で開くと、LINEなどのアプリ内ブラウザでブロックされて何も起きないことがある。通常の `<a href target="_blank">` にする
- **テスト閲覧を除外**: プレビュー表示・動作確認用のURL（例 `?preview=`）では `gtag('config')` を呼ばない。config しなければページビューもイベントも送られない
- **外部の認証をはさむ流れ**（OAuthなど）: アプリ内ブラウザから外部アプリ・別ブラウザに切り替わると、GAでは別人として数えられる。GAのリンカー（`_gl`）はブラウザが変わると無効になるので効かない。診断開始時に `gtag('get', GA_ID, 'client_id', cb)` で client_id を取り、OAuth の `state` に入れて持ち回り、戻った先で `gtag('config', GA_ID, { client_id })` に指定してからURLから消す
- **GA側の設定**（実装と同時に依頼する）: CVのキーイベント指定、パラメータをレポートで見るためのカスタムディメンション登録（イベント単位／ユーザー単位）。**カスタムディメンションは登録した時点以降のデータしか集計されない**ので早めに登録する

## 4. 動作を確かめる

- ブラウザ自動操作（Playwright など）で各ボタンを実際に押し、`window.dataLayer` に期待したイベントとパラメータが1回ずつ積まれることを確認する。GAのスクリプトはモックして本番データを汚さない
- テスト用の測定ID（例 `G-TEST`）でビルドして確認する
- 除外したいページ（プレビュー等）で `config` が呼ばれていないことも確認する
- 本番では GA の DebugView かリアルタイムで1回だけ確認する

## 5. 数字の妥当性を確かめる

数字を見たら、判断に使う前に次を確認する。

- **ファネルは後ろの段ほど人数が減るはず**。後ろの段が前より多いときは計測の不具合を疑う（下の表）
- **回数とユーザー数を分けて見る**。テストで1人が何十回も押すと回数だけが膨らむ。効果の判断はユーザー数で行う
- **レポートは数時間遅れる**。当日の数字で結論を出さない
- **人数が少ないうちは傾向として扱う**（目安: 1つの区分が30件未満なら断定しない）。A/Bテストの差は1パターン数百人ないと偶然と区別できない
- 実データと突き合わせられるものは突き合わせる（例: アプリが表示する頻度と、元データから数えた頻度）

## 6. 違和感から原因を特定する

| 症状 | 疑う原因 | 対処 |
|---|---|---|
| 後ろの段のユーザー数が前より多い | 外部認証でブラウザが切り替わり別人扱い / プレビュー・テストの閲覧 / 結果URLの開き直し | client_id の持ち回り / テストURLを計測から除外 / 回数ではなく到達人数で見る |
| 1人で回数が極端に多い | 開発者のテスト | ユーザー数で判断。必要なら GA の内部トラフィック除外（IP） |
| カスタムディメンションが `(not set)` だけ | 登録前のデータ / パラメータ名の不一致 | 登録日以降で見る / 送信側のパラメータ名と一致させる |
| ボタンを押しても何も起きない・計測されない | アプリ内ブラウザでの `window.open` ブロック | 通常のリンクにする |
| 特定の値に偏る（例: 判定結果の8割が同じ） | ロジックの重み付け・正規化範囲の問題 | 架空の利用者集団でシミュレーションして分布を確認 |
| 実感と数字がずれる | 数え方の定義の問題（件数と日数、屋内と屋外の混在など） | 元データと突き合わせて定義を見直す |

## 進め方の約束

- 設計（どのイベントを・何のために・何を送らないか）を先に短く示し、合意してから実装する
- 変更したら、計測内容の一覧（イベント・発生箇所・パラメータ）をプロジェクトのドキュメント（CLAUDE.md など）に残す。次に数字を読む人が定義を確認できるようにする
- 数字を報告するときは、注意点（テストの混入・遅延・少人数）を必ず添える
